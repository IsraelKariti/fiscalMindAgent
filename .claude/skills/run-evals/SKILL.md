# Run evals

The harness in `evals/` sends **exactly what the app sends** (the same `build*Call` builders through
`runLlmCall`, with a per-call `model` override and a file log sink — nothing lands in `llm_calls`),
passes every answer through the stage's code gate, and judges it **in code**. Real runs cost money.
Prefer the free paths first.

## Decide which path

| Situation | Command | Cost |
|---|---|---|
| A case's `expected` or a judge in `evals/stages.ts` changed | `npm run evals:rejudge` | free |
| Just need the numbers / the page | `npm run evals:report`, open `evals/results/report.html` (or `npm run evals:serve`, port 3211) | free |
| Prompt, schema, gate or `build*Call` changed | targeted run: 1 stage, 1-2 cheap models | cents |
| Model comparison, or the owner asks for a full run | full run (all stages × the available models) | dollars |

Never start a full run to answer a question the stored `evals/results/latest.json` already answers.

## Before a paid run

1. `npm test` and `npm run typecheck` must be green (the harness imports the app code).
2. `.env` has the key of every provider in the model list (`GEMINI_API_KEY`, `OPENAI_API_KEY`,
   `ANTHROPIC_API_KEY`). The database does not need to be reachable.
3. Note the harness's own spend cap `EVALS_MAX_SPEND_USD` (default 30). Set it low for a smoke run.
   The production spend cap (admin Settings) does not apply to harness calls.
4. Save the baseline: `latest.json` is overwritten by every run, but each run also writes
   `evals/results/run-<timestamp>.json`. Note the current latest's timestamp before starting.

## Commands

```
npm run evals -- --stages file_classification --models gemini-2.5-flash --concurrency 2 --out evals/results/smoke.json
npm run evals -- --cases <id>,<id> --models gemini-2.5-flash,gpt-5.6-luna
npm run evals -- --stages questionnaire_schema_mapping,extract_document
npm run evals                                   # full run: every stage × every model whose key is set
npm run evals:rejudge -- --in evals/results/run-<ts>.json
```

Flags: `--stages a,b`, `--models x,y`, `--cases id,id`, `--concurrency N`, `--out file.json`
(`--out` keeps `latest.json` untouched: use it for smoke runs). Stages: `injection_detection_llm`,
`questionnaire_schema_mapping`, `file_classification`, `extract_document`, `generate_message`. Default models are the
platform's `LLM_MODEL_OPTIONS` filtered by available keys (`evals/run.ts`). Test PDFs live in
`evals/files/`; regenerate the synthetic ones with `npm run evals:files` (needs Chrome).

## After the run: compare, do not just report

Read `summary[stage][model]` from the new file and from the baseline file. Report per stage:

- pass rate before and after, per model,
- which case ids flipped (pass → fail is a regression; list the `checks` with `pass: false`,
  `expected` vs `actual`),
- `errors` (schema refusals, timeouts) separately from failed checks,
- avg latency and `costUsd` only if they moved by more than about 20%.

A case that fails on **every** model after a prompt change usually means the expected value or the
judge is wrong, not the models. Fix the case and re-judge instead of re-running.
A case that fails on one weak model only is not a regression of the prompt.

Show `results[].output` for a failing case when explaining it; the parsed answer is stored there.

## Choosing models

The point of the matrix is the per-purpose model setting (admin Settings → מודל השפה, one picker
per purpose). Pick per purpose: the cheapest model that passes every regression case, latency second.
Keep the run file as the justification.

## Writing results back

- Keep `run-<ts>.json` files; never delete them (the report page and comparisons use them).
- `latest.json` and `report.html` are regenerated by a run; commit them only when the owner asks.
- Cost is `null` for a model missing from LiteLLM's pricing registry (`src/gemini/pricing.ts`).
