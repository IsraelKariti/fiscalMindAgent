# Add an eval case

Every LLM stage has cases in `evals/cases/<stage>.json`. A case is an input plus `expected` values.
The judge is **code** in `evals/stages.ts` (never another model): it runs the stage's gate, then
compares the listed fields. A field that is not in `expected` is not checked. A list in `expected`
means "any of these is accepted".

Add a case whenever a bug was fixed, a prompt or gate changed behaviour, or a real client document
showed a shape we did not cover. One behaviour per case.

## Steps

1. Pick the stage and read its case file. Copy the closest existing case.
2. Give it the next id in that file's series (two digits, keep order).
3. Fill `notes` with one sentence: what this case proves and why it exists (bug, date, document).
4. If it needs a document, see "PDF cases" below.
5. Decide `expected` from the **app's rules**, not from what a model happened to answer: the gate in
   the stage's `*Rules.ts` (`formIntakeRules.ts`, `analyzeFileRules.ts`, `injectionScanRules.ts`,
   `verifyChecks.ts`, `decisionSchema.ts`) and the shared context at the top of the case file
   (`taxYear`, `checklist`, `client`).
6. Judge it. `npm run evals:rejudge` is free but only re-judges case ids that already have stored
   outputs. A new id needs one paid call:
   `npm run evals -- --cases <id> --models gemini-2.5-flash --out evals/results/smoke.json`.
7. If a strong model fails the new case, doubt the case before the model: re-read the prompt
   (admin → LLM stages, or `describeLlmStagesStatic()` in `src/gemini/llmStages.ts`) and the gate.
   Fix `expected` or the judge, then re-judge.
8. Update the "Cases" column for that stage in `evals/README.md`.
9. Run `npm test` (a judge change can break imports).

## Case shapes

See the existing files — each stage's file documents its own shape in a top-level `judge` field.
Stage keys: `injection_screen`, `form_intake`, `analyze_file`, `verify_document`, `conversation_decide`.

- `injection_screen`: `kind: "text"` with `snippets[]`, or `kind: "file"` with `file`/`contentType`/
  `filename`; `expected.suspected_injection`. Keep the benign/attack balance — a benign case with a
  scary word ("ignore", "system") is worth more than another plain attack.
- `form_intake`: `answers` keyed by the platform's questionnaire questions; `expected.verdicts` per
  `type_key` (`required | not_required | unclear`), `expected.instances.<type>` as lower-case
  substrings one per instance, `expected.dropped` (normally 0). The catalog has 17 types
  (`declarationOfCapital/catalog.ts`) — special keys the prompt names (real_estate splitting, vehicle
  two instances, mortgage from a real-estate answer, savings family, prior_declaration our/another
  office) each deserve a case.
- `analyze_file`: `expected.document_type` (a catalog key or `other`), `matched_document_id`
  (`null`, an id, or a list), `legible`, `injection_suspected`, `document_kind_any`.
- `verify_document`: `doc` (`name`, `description`, `type_key`), `client` (`name`, `idNumber`),
  `expected` fields (`is_expected_type`, `subject_id_number`, `as_of_date`, `valid_until`, `amount`
  `{value, currency}`, `subject_name_matches`, `legible`, `injection_suspected`) and
  `expected.verdict` = what `runChecks()` must decide (`passed`, `failed_keys` by check key —
  reasons are Hebrew, never match on text).
- `conversation_decide`: a state snapshot; hard code asserts only (decision, channel, valuation date
  mentioned, ≤3 questions, every resolution with a verbatim quote). No LLM judge.

## PDF cases

- Real documents go in `evals/files/` and are referenced by name. Never add a real client's document
  without the owner's OK; the two real files present (`hapoalim.pdf`, `peper.pdf`) are his.
- Synthetic documents are generated by `evals/make-files.ts` (headless Chrome) for the fictional
  client ישראל ישראלי, ID `123456782`; add an entry there, then `npm run evals:files`. Hide an
  injection payload the way an attacker would (white 1px text, tiny footer).
- A new PDF usually serves three stages: `injection_screen` (file kind), `analyze_file` and
  `verify_document` — add it to all three in the same change.

## Do not

- set `expected` by copying a model's output you have not checked against the document,
- use an LLM as the judge, or a fuzzy string score; add a code check to `evals/stages.ts` instead,
- change an old case's `expected` to make a run green without a note explaining the new truth.
